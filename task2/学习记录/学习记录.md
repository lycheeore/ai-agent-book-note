## 1. 一句话总纲

第 2 章管的是「**这一次**任务里模型该看到什么」；第 3 章管的是「**任务结束之后**，Agent 还能记住什么、查什么」。

本章把持久化知识切成两个尺度——**用户记忆**（服务单个用户，目标"懂你"）与**共享知识库**（服务所有用户，目标"领域专家"）。两者共用向量检索与知识压缩，也共用同一批麻烦：信息冲突、知识过期、检索不准。而全章最终收敛到**一个**工程结论：

> **把知识原料直接丢进库是不够的。** 检索的质量上限，在索引阶段就被定死了——分块切断了上下文，原始案例掩盖了统计规律，扁平文本丢掉了层次与关联。所以要在索引期投算力去**提炼、抽象、结构化**。

## 2. 记忆系统的三套分类体系（正交，可自由组合）

这是本章最容易混的地方，正文用表 3-1 一次性厘清：

| 分类体系 | 回答的问题 | 具体类别 |
| :-- | :-- | :-- |
| **记忆层次** | 存在哪里？ | 轨迹（当前会话，append-only）／用户长期记忆（跨会话，反复改写）／业务状态（任务阶段） |
| **存储格式** | 怎么存？ | Simple Notes／Enhanced Notes／JSON Cards／Advanced JSON Cards |
| **认知类型** | 存什么？ | 情景记忆（具体事件）／语义记忆（一般知识）／程序记忆（行为流程） |

一条"用户偏好靠窗座位"的语义记忆，可以用 Simple Notes 存在用户长期记忆里；一段"先搜直飞→确认座位→用常旅客号"的程序记忆，可以用 Advanced JSON Cards 存。**选格式是工程取舍（简单 vs 表达力），选类型是业务取舍（事实 / 事件 / 流程）。**

补充两组近义概念的边界（正文专门划清过）：

- **轨迹 vs 工作记忆**：都为当前决策提供上下文，但轨迹是**不可变**的完整事件序列（按时间追加），工作记忆是经过筛选激活的**动态子集**（按相关性裁剪）。
- **词义消歧 vs 实体消歧**：前者靠上下文感知嵌入（"bank"是河岸还是银行）；后者需要维护实体本身的知识（两个"张医生"），在图谱里是节点而非推理问题。

## 3. 记忆的评估：先立标尺，再谈方案

正文先归纳了八项记忆能力（个人信息保留 / 偏好追踪 / 上下文切换 / 记忆更新 / 多会话连续性 / 复杂思考 / 时间感知 / 冲突解决），并明确说明这是**笔者的归纳口径**，不是 LoCoMo 等基准的原始分类（LoCoMo：平均约 300 轮、最多 35 个会话）。再据此设计贴合 Agent 场景的**三层次评估框架**（每层 20 个用例，来自 `user-memory` 项目）：

| 层级 | 要求 | 典型用例 |
| :-- | :-- | :-- |
| 一 · 基础回忆 | 精确存取结构化无歧义信息 | "我的会员号是 12345" |
| 二 · 多会话检索 | 跨对象、跨时期检索并推理判断 | 有两辆车，问"为我的车预约保养"→ 应反问是哪辆 |
| 三 · 主动服务 | 无明确指令下预见性整合 | 订国际航班时关联数月前的护照信息并预警过期 |

## 4. 四种存储格式：粒度与结构的递进

| 格式 | 优势 | 代价 | 失分场景 |
| :-- | :-- | :-- | :-- |
| **Simple Notes** | 最小不可再分事实，O(1) 开销极低 | 信息关联性完全丢失，需重新拼凑 | 第二、三层"需综合多条信息"的用例频繁失分 |
| **Enhanced Notes** | 保留叙事结构，语义完整丰富 | 存储冗余、属性变更要重写多段 | —— |
| **JSON Cards** | 三层嵌套，支持部分更新，可预测可扩展 | 刚性结构，多维信息被强行归一 | "周末用 Python 开发个人项目"同时涉时间/技术/活动，归哪一类都丢 |
| **Advanced JSON Cards** | 加 backstory / person / relationship / 时间戳，解决消歧 | 生成与维护成本最高、最慢 | —— |

选型标准：**关键且少量**（用户偏好、关键人物关系）→ Advanced JSON Cards；**大量且非关键**的对话事实 → Simple Notes；生产系统为混合模式。

正文的实验 3-2 观察与上述分析一致：Simple Notes 以最低成本通过第一层多数用例，但在需要综合信息、区分同名实体的二三层频繁失分；Advanced JSON Cards 在消歧与跨会话关联上最好，代价是每次会话结束后的记忆维护调用明显更贵更慢。

**超越文本：可执行记忆（User as Code）。** 四种格式本质上都是文本，擅长召回单条事实，却把聚合、冲突检测、约束执行交给 LLM"心算"。User as Code 把用户状态改成带类型的可执行对象、规则写成普通函数，借鉴"预写日志 + 检查点"：会话后先追加到只增日志，再定期从完整日志重建带类型状态。于是聚合（`count(trip for trip ...)`）、冲突发现（用药 × 过敏史交叉比对）、约束执行（出票前检查护照有效期 < 180 天就告警）都变成确定性函数，**表示与推理使用同一种可验证介质**。

## 5. 记忆框架的两个真实取舍（Mem0 / Memobase）

- **Mem0 的架构演进很值得记**：2025 论文与 v2 把冲突处理放在**写入阶段**——抽取候选事实 → 向量检索相近记忆 → LLM 在 ADD/UPDATE/DELETE/NOOP 中决策（"住北京"→"搬上海"直接 UPDATE 覆盖）。优势是库始终简洁一致；风险是一次错误 UPDATE/DELETE **不可逆地丢失历史**，且每条候选都要过一遍检索 + 第二次 LLM 判断。2026 年 v3 改为**仅追加写入 + 检索时推理**：只做 ADD，两条带时间的事实并存，查询时融合语义相似度、BM25、实体匹配并按时间排序。报告指标 LoCoMo 71.4 → 92.5、LongMemEval 67.8 → 94.4。
- **Memobase 走"用户画像 + 事件记忆"**：Profile 是按主题—子主题两级组织的可配置槽位；Event Memory 按时间线记录经历。工程上用**缓冲批处理**摊薄 LLM 调用，查询侧只读整理好的画像与事件，保证低延迟。

> 一个方法论收获：**"写入时消歧"和"读取时消歧"是一次典型的位置权衡**——前者省查询算力、库更干净，但错误不可逆；后者保留全部证据、LLM 调用更少，代价是把判断推到每次查询。这与第 2 章"压缩 vs 隔离"是同一类取舍：**代价不会消失，只会转移**。

## 6. 记忆压缩与整理：三层机制

1. **重要性评分筛选**：访问频率、时间衰减、情感强度、信息独特性四个因素综合打分，低于阈值标为可压缩/可删除。
2. **聚类**：相似记忆分组，每组生成代表性摘要（多次天气对话 → "用户经常询问天气，特别关心降雨"），原始详细记忆归档二级存储。
3. **抽象泛化**：从情景记忆提取一般规律，转化为语义/程序记忆（多次购物对话 → "偏好性价比高、重视评价"）。

此外本章专门讨论了**隐私保护：日志脱敏**（实验 3-3）——用本地 Ollama 小模型而非云端 API 做 PII 检测，理由是"把含敏感信息的日志发到云端脱敏就违背了隐私保护初衷"。识别结构化（身份证/银行卡）、半结构化（地址）与自然语言（"我的密码是 abc123"）三类，JSON Schema 结构化输出类型/位置/置信度，召回率 95% 以上，显著优于纯正则。高吞吐场景用"正则粗筛 + LLM 深析"的混合策略。

## 7. RAG：从管道到探索者

### 7.1 为什么"直接丢进库"不行——两个奠基案例

这两个案例是本章前半段的核心论证，Task1 笔记完全漏掉了：

**案例一 · 黑猫白猫的计数问题**：知识库有 100 个独立案例文档（90 黑猫 / 10 白猫），用户问"比例是多少"。受 top-k（如 20）限制，大部分案例根本不会被检索到，模型只能基于不完整样本（15 黑猫 / 3 白猫）得出错误结论。**光有 RAG 不够，因为"检索到的部分"不等于"统计上的全体"。** 解法：索引前预先生成摘要"共 100 只，90 黑猫(90%) / 10 白猫(10%)"，一次检索就能拿到准确答案。

**案例二 · Xfinity 优惠资格的边界问题**：知识库是几百条客服工单，每条只记录一个个案结论（退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 不符合……），没有任何一条写着规则本身。护士来问"我能不能享受优惠"，会遇到三重障碍：
- **最近邻偏置**——"护士"与"医生"语义最近，Sarah 那条排最前，模型顺势推断护士也可以；换 Mike 那条排前面，同一个问题会得到相反答案；
- **边界语义的缺失**——"仅限……，其他一律不适用"这种全称与否定的边界，**不存在于任何单条工单中**，调大 k 也解决不了；
- **完整性信号的缺失**——模型无从判断自己是否看全，于是不追问，只照着手里几条自信作答。

解法仍在索引期：离线通读整个工单库，提炼出规则卡"适用于现役与退伍军人、持证医护人员（含护士）；教师等不适用"。

> **两个案例指向同一结论**：无论存向量库、检索后注入，还是直接塞进长上下文，**未经提炼与结构化的知识，模型都无法可靠利用**。必须在索引阶段投入计算资源做提炼、抽象、结构化。

### 7.2 分块：一切残缺的源头

分块必不可少的两个原因：嵌入模型有长度限制且多主题混合会稀释向量（与 Enhanced Notes 的问题同源）；检索目标只是注入**相关的那部分**。

三类策略：固定大小切分（简单可预测，会拦腰截断结构）／**递归、结构感知切分**（生产默认）／语义切分（质量高但要多算嵌入）。块大小是典型权衡，实践起点 **256–1024 token、重叠 10%–20%**。

> 分块的**固有缺陷**：无论哪种策略，都会切断片段与原始上下文的联系——"该公司"指代谁、出自哪份报告，全留在块外。这是后文"上下文感知检索"要正面解决的问题。

### 7.3 两条检索路线：互补而非替代

| | 稀疏嵌入（BM25） | 稠密嵌入 |
| :-- | :-- | :-- |
| 依据 | 词频与逆文档频率，精确词项匹配 | 深度学习映射到向量空间，余弦相似度 |
| 为什么用**夹角**不用距离 | —— | 关心**方向**（语义）而非**长度**（文本长短）：内容相同但长度不同的文档，向量长度不同、方向一致 |
| 强项 | 技术代码、错误码、人名、ID | 语义改写、跨语言、同义表达 |
| 盲区 | 同义表达（搜 kitty 找不到只写 cat 的文档） | 近似编码（XR-7001/7002/7003 向量几乎不可区分） |

BM25 相对 TF-IDF 的两处修正：**词频饱和**（$k_1$，使重复出现的边际贡献递减）与**长度归一化**（$b$）。IDF 也换了更稳健的写法 $\ln\frac{N-DF+0.5}{DF+0.5}$——分子是"不含该词的文档数"，比值直接表达"不含它的文档是含它的多少倍"，各加 0.5 平滑使 DF 取 0 或 N 时仍有定义；代价是词出现在超过半数文档时会取负值，实现中通常设下限。

### 7.4 混合检索流水线：三阶段各司其职

```
查询 ──┬─▶ 稠密检索 ─┐
       └─▶ 稀疏检索 ─┴─▶ 融合（RRF / 加权）─▶ 重排序（跨编码器）─▶ 生成
```

- **融合**：两路得分不可直接比较（余弦 0–1，BM25 0 到几十），**RRF** 干脆丢掉原始得分只看排名，$score=\sum 1/(k+rank)$，$k$ 常取 60 压低前几名之间的差距；简单稳健，但丢失丰富相关性信号。**加权融合**保留原始信号，代价是要先 min-max 对齐两路量纲。
- **重排序**：不是"补救 RRF 丢掉的得分"，而是**换用更强的匹配范式**——跨编码器把查询与文档拼接后逐词比对，精度远高于检索阶段双编码器各自独立编码再比相似度。正文的比喻很贴切：**双编码器是猎头快速筛简历，跨编码器是面试官与候选人深谈**。重排**不替代**融合：融合负责产生统一候选池，重排在候选池上精排。
- ⚠️ **关键边界**：重排只能对**已经进入候选池**的文档重排。前面漏掉的，后面补不回来。所以"该改召回还是改排序"必须先看阶段指标才能判断。

**检索质量三指标**（表 3-3）：recall@k（该找的找到了吗）/ MRR（找到得够不够靠前）/ nDCG（整个排序列表质量如何）。工业界另有"检索失败率"= 正确信息未出现在 top-20 的比例。

> 一处必须诚实标注的口径差异：书中此处的"recall@k"实为**命中率**（hit rate / success@k）——只要前 k 名里有一篇相关文档就算命中；学术标准 recall@k 指"相关文档被召回的**比例**"。书中为与 Anthropic Contextual Retrieval 报告口径一致而沿用简化写法，跨来源比较时要留意。

### 7.5 超越扁平文本：知识怎么组织

| 方案 | 机制 | 擅长回答 |
| :-- | :-- | :-- |
| **RAPTOR** | 自下而上：叶子节点聚类 → LLM 生成父节点摘要 → 递归成树 | "从概念逐步钻进细节"（跨层穿梭） |
| **GraphRAG** | 实体—关系三元组 + 社区发现生成摘要 | "A 和 B 之间是什么关系"、多跳推理、**实体消歧**（图结构原生能力） |
| **OpenViking（文件系统范式）** | 记忆/资源/技能映射为 `viking://` 虚拟文件，**L0 摘要(~100 token) / L1 概览(~2k) / L2 全文**按需加载 | 轻量、可读可改可 Git 回滚的知识组织 |

几条正文里容易被略过但很硬的判断：

- **知识图谱作为用户记忆的通用方案有固有局限**：自然语言转三元组必然**语义降级**——"如果下周还下雨，我就取消去海边，改去博物馆"只剩（我, 有计划, 海滩旅行）和（我, 有备选, 博物馆），条件逻辑与时间依赖全丢。推荐策略是**分层互补**：完整自然语言保核心信息，结构化元数据做索引，图谱只在多跳推理/精确消歧的垂直场景做专项索引。
- **文件系统范式的前提是"链接与索引"**：只有纵向的 `.abstract`/`.overview` 不够，还要横向交叉引用——知识库要像 Wikipedia，每个条目提到别的条目就链接过去，配入口页与索引页。否则文件越多越难检索。而且**不同模型主动建链的意愿差异很大**，提示词里必须把"新增条目要先检索并链接已有条目、更新索引页"写死。
- **结构化索引不是默认选项**：查询主要是"找到包含某信息的片段"→ 混合检索就够；经常需要**跨文档综合**或**多层次导航**时才值得投入，代价是索引与查询都多花 LLM 调用。

### 7.6 知识怎么更新：把知识库当代码库

**增量更新 = 知识变更走 PR**（正文反复强调这条不只适用于 User as Code，Markdown 记忆库、规则文档同样应进 Git）：

1. **Proposer Agent 提交 PR**：从原始证据发现新事实/冲突/过期内容，在工作分支提**尽可能小而完整**的 diff——不是把最新对话粗暴追加到文件尾，而是先检索相关已有知识，再增删改条目，同步维护链接、索引、时间元数据与证据引用。
2. **Reviewer Agent 独立审核**：拿到变更前知识 + diff + 原始证据，独立检查每个断言是否被证据支持、是否漏限定条件、是否与其他文件冲突、删除改写是否过度；不通过要给**指向具体证据与行号的可执行意见**，不能只说"还需要改进"。
3. **迭代至收敛**：设最大迭代次数或成本预算，超限转人工，**不能默认放行**。
4. **合入后再发布**：CI 检查格式/链接/元数据/权限，再**从已合入版本增量重建**受影响的分块、摘要与向量索引——**索引是可重建的派生物，Git 中已审核的知识才是来源**。

三条配套要求：

- **分层**：原始证据层（只增不改的对话/轨迹/原始文档）／知识层（提炼后可持续修订的 Markdown 或代码）／服务层（从某个已合入版本生成的检索索引）。每条线上知识都能回答"从哪条证据而来、谁在什么时候批准"。
- **Proposer/Reviewer 必须是 Agent，不是两次固定 LLM 调用**——它们要主动搜索其他相关记忆与规则、追溯证据、对比文档、运行检查，需要文件搜索/版本比较/测试执行/证据检索工具，现成 Coding Agent 通常就能胜任。
- **两个 Agent 用能力相近但不同家族的模型**（Claude × GPT，或 DeepSeek × Kimi），降低同处犯同类错误的概率；**异源互审增加独立性但不替代原始证据**，Reviewer 要核对证据与 diff，而不是顺着 Proposer 的结论再讲一遍。权限强制分工：Proposer 只能写工作分支，Reviewer 只读证据并提交审核结果。

**定期整理 = 睡眠学习在知识管理中的实现**（前台累积，后台在周期窗口从全局重审），三件事：① 去重去旧合并（重新建链、建入口页索引页，必要时拆大文件合小文件；删的是知识表达，不是下层只增不改的原始证据）；② **回到原始数据核查**（不能只在摘要之间互改，否则早期遗漏会一代代传下去；分批扫描要保留**覆盖清单**确保全量）；③ **冲突解决与场景限定**——不简单"保留最新一条"，而是追溯各自来源，看是否分别在不同时间/对象/地域/任务/前置条件下成立；都有效就把适用场景写进知识，证据不足就**保留冲突与待确认状态，不得强行收敛**。

还有两条生产约束：**失效内容检测与下线**（给分块附版本号与生效/失效时间，检索阶段就过滤，或在摘要标注"此条已于某日废止"）；**多用户共享的权限与租户隔离**（检索必须按调用者权限过滤，**权限过滤要下推到检索层**——一旦敏感内容进了 LLM 上下文，就很难保证不泄露；多租户还要隔离向量索引与元数据，避免"串味"）。

### 7.7 智能体化 RAG 与上下文感知检索

| | 非智能体化 RAG | 智能体化 RAG |
| :-- | :-- | :-- |
| 形态 | 单向数据流，被动的"检索-生成"管道 | ReAct 循环主导的动态迭代探索 |
| 比喻 | 在图书馆只能搜一次就得立刻写报告 | 一位研究员，可反复查阅不同书架、调整策略、交叉验证 |
| 适用 | 信息需求明确单一（更快） | 多跳、复杂问题（更稳） |

正文的实验 3-8 用中文司法问答验证了这一点：简单问题（"正当防卫怎么规定"）两者相差无几；复杂问题（"醉酒过失致人重伤且有盗窃前科如何量刑"）差距显著——智能体化 RAG 会分解问题 → 并行搜索 → 评估缺口 → 构造更精确的二次查询 → 综合。**它的价值是"解决问题"而非"回答问题"。**

**RAG 的安全边界**：检索到的文档正是**间接提示注入**最典型的载体（知识库投毒是同一道理，只是污染发生在索引之前）。两层防御：① **指令与数据分离**（给检索内容做来源标记，明确"这是资料不是命令"）；② **不让检索内容直接触发高风险操作**（转账/删除/对外发信必须有独立授权判断，不能仅凭检索文本自动执行）。执行层防御在第 4 章展开。

**上下文感知检索（Contextual Retrieval）**：索引前为每个 chunk 用 LLM 生成包含核心背景的**前缀摘要**，再与前缀拼接后索引。它同时增强两种检索——对 BM25 增加了可精确匹配的关键词（"ACME"、"2025 Q2"），对嵌入注入了语义背景。Anthropic 数据：**结合 BM25 使检索失败率降低 49%，再加重排序达 67%**；代价是索引期额外 LLM 调用，但靠 prompt caching 可控（每百万文档 token 约 1 美元）。

> ⚠️ 必须与第 2 章划清界限：**上下文感知检索在索引期对文本块做加法（补前缀）**，**上下文感知压缩在运行期对对话历史做减法（去冗余）**。名字相近，时机、对象、方向全都相反。

### 7.8 本章的收口：双层记忆架构

把知识库技术**反过来**用到用户记忆上，得到本章最终形态：

- **实验 3-9（智能体化 RAG）**：把完整对话历史当知识库，按固定窗口（如每 20 轮）分块索引，并给 Agent `search_user_memory` 工具。第一层一次搜索即可；第二层见效（本田 + 特斯拉两辆车，"为我的车预约"→ 先搜到本田 → 发现还有特斯拉 → 二次搜索 → 反问是哪辆）。但**更复杂的第二层用例暴露局限**：`12_contradictory_financial_instructions.yaml` 中妻子设立转账 → 丈夫改金额日期 → 妻子再改回来，孤立分块让系统看到**三个各自独立却相互矛盾**的指令，无法判断哪条最终有效。
- **实验 3-11（上下文感知检索增强用户记忆）**：给每个对话块补上 `[妻子 Patricia 正在设立初始电汇]`、`[丈夫 James 正在修改之前的电汇]`、`[妻子在丈夫修改后再次修改电汇]` 这类前缀后，**事实冲突**的处理出现决定性改善——时间、人物、意图成了判断优先级的线索。
- **最高级的第三层（主动服务）需要双层结构**：**Advanced JSON Cards 常驻上下文**（少量关键事实，如"护照 2025-02-18 过期"）+ **上下文感知检索按需取细节**（原始对话）。只有同时握有"全局概览"与"精确细节"两种视角，才能发现"一月机票 + 二月护照到期"这种跨会话隐藏关联。

> 回看实验 3-1 立的三层标尺：**基础回忆靠可靠存取即可满足；多会话检索靠检索技术补齐；主动服务最难，因为它要求两种视角同时在场**——只靠常驻上下文会因容量受限丢细节，只靠检索会因缺乏全局视野发现不了隐藏关联。

### 7.9 两条前沿与一个哲学问题

- **多模态记忆**三条思路：① 存原始多模态数据 + 文本描述索引；② 把多模态嵌入压缩进上下文（**每个嵌入只占 1 个 token 空间**，1000 token 区域可容纳 1000 张人脸，效率极高）；③ 把嵌入写进模型参数——朴素做法是每用户训 LoRA，但 fact-LoRA "直接提问几乎完美复述，一旦需要在事实上做间接推理便失灵"，因为冻结的骨干模型从未学过如何"查阅"这个临时挂载的适配器。User as Engram 改为把嵌入写入 Engram 模型空闲的**哈希 N-gram 槽位**（预训练时已学会哈希查表，配有上下文感知门控决定何时调取）。
- **从结构化数据集中提取深度知识**（实验 3-12）：司法判例的"知识"不在法条里，而在成千上万份判例的权衡经验中。流程是"因子发现 → 聚类原型 → 对话式建议"：用 LLM **自下而上**从数百样本中自由列出影响判决的因素（构建核心模式 + 按罪名的扩展模式），把案件转成数字（罪名用 one-hot 而非 1/2/3，避免暗示大小关系），聚类找"案件原型"，形成因子重要性层次模型，再驱动 Agent 按重要性顺序向用户提问补全信息、检索最相似原型给出有判例支持的分析。**Agent 不必把知识库当只能检索的静态仓库——可以先把数据读懂，提炼出决策逻辑，再基于逻辑回答。**
- 思考题里最尖锐的一条是 Rich Sutton 的**苦涩的教训**：本章构建的分块策略、索引结构、检索管道，是否本身就是一种"手工设计"，会被更强的模型 + 全量输入取代？

## 9. 打卡核心问题：重新理解 RAG 与记忆

### 9.1 一句话回答

**Context 是唯一的出口，Memory 和 RAG 都是入口；本章补上了关键的一半：入口的质量，在索引期就已经被决定。**

### 9.2 三个判断句（在 Task1 基础上修正/加厚）

1. **RAG 不是"检索 + 生成"两步，而是一条五阶段流水线，且各阶段职责不可互相代偿。**
   分块 → 稠密/稀疏检索 → 融合 → 重排序 → 生成。实验 3-6 的真实数据（见实验记录）显示：**BM25 与 Dense 的失分点几乎不重合**（BM25 在语义改写与中文跨语言上翻车，Dense 在近似编码上翻车），而 **RRF 融合把两者一起救回满分**；但重排序**只对已进入候选池的文档生效**——这正是"先看召回，再看排序"的顺序。

2. **Memory 与 RAG 是同一套技术的两个尺度，不只是"用户 vs 集体"的区别。**
   本章真正的论证结构是：**先在知识库尺度上把检索技术做成熟（3-4~3-10），再反过来把它应用到用户记忆（3-9、3-11）**。所以"Memory 是用户尺度的 RAG"不只是比喻，而是**实现路径**：连失败模式都一样——孤立分块导致相互矛盾的记忆并列（转账三方修改用例），解法也一样（补上下文前缀）。

3. **记忆的终点不是"存下来"，而是"能在对的时刻被主动想起"。**
   三层次评估框架给出递进标尺，而第三层"主动服务"无法靠单一技术达成——必须**结构化概览常驻 + 非结构化细节按需**的双层结构。这与第 2 章"压缩与隔离"是同一个道理的两种表现：**全局视野与精确细节，天然需要两套载体。**

### 9.3 与 Context / Memory / RAG 三表对照（修订版）

| | **Context** | **Memory** | **RAG** |
| :-- | :-- | :-- | :-- |
| 本质 | 一次调用里模型实际看到的内容 | 跨会话持久化的用户档案 | 从外部知识取回片段并注入上下文的管道 |
| 时间尺度 | 本次任务（秒~小时） | 跨任务（天~年） | 随知识库更新 |
| 服务对象 | 当前这一次决策 | 单个用户 | 所有用户 / 某个领域 |
| 主要技术 | 消息角色、KV Cache、提示工程、Skills、状态栏、**运行期压缩** | 事实抽取、抽象、结构化管理、冲突消解、**PR 式更新 + 定期整理** | 分块、稀疏/稠密嵌入、融合、重排、结构化索引、**索引期补上下文** |
| 失效模式 | 溢出 / 腐化（Context Rot） | 冲突、过期、消歧失败、错误 UPDATE 不可逆 | 漏召回、最近邻偏置、边界语义缺失、间接提示注入 |
| 本章的边界 | —— | 本章建的是全书发现循环的"**提案**"段 | 质量上限由**索引期**决定 |

## 10. 待深入的问题

1. **上下文感知检索会不会放大错误？**（思考题 2）如果原始文档本身结构混乱或含矛盾，补前缀会让"错误被更好地检索到"。怎样在检索阶段引入"信息质量"信号？
2. **RRF 的 k=60 凭什么是默认？** 实验 3-6 的真实扫描显示在本语料上 k 完全不敏感（指标已饱和），要看到 k 的作用，需要什么样的语料分布与多大的候选池？
3. **"权重为 0"与"关闭通道"不等价**（本次实验实测发现）：融合实现里权重只乘分数、不做过滤，零分文档仍占候选位。那么生产代码里该怎样正确表达"降权"与"禁用"？
4. **双层记忆的常驻部分该放多少？** Advanced JSON Cards 常驻上下文，但常驻就意味着成本与 KV Cache 压力。多少张卡片之后应该改为索引化？
5. **异源互审的独立性上限**：Proposer 与 Reviewer 用不同家族模型能降低同类错误概率，但两者面对的是同一份被挑选过的证据。如果证据覆盖不完整，独立性还剩多少？
